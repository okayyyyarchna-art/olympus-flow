# Decision inventory: table visibility after rebalance (faust @ 3442a90f)

Requirement (user's words): after a rebalance a worker's table shows only the partitions it actively owns, however the
table is read, with the in-memory store and with RocksDB. Partitions it keeps keep all their data. Partitions it takes
over show up once recovery is done. GlobalTable still shows everything on every worker. A timer walking the table
must not crash with "dictionary changed size during iteration" when a rebalance lands mid-iteration.

All paths are relative to the repo root `faust/` (the checkout).

## Background facts the rows rely on

- Every Table read goes to the store: `Collection.data` is the store (faust/tables/base.py:213-219, faust/tables/table.py:22-26),
  and the store is a mode `FastUserDict` (faust/types/stores.py:6, faust/types/stores.py:32). The in-memory store keeps a plain
  dict (faust/stores/memory.py:15). How `FastUserDict` maps `items()/keys()/len()/in` onto that dict lives in the
  `mode` package, outside the folder I may read, so I do not count any finding that depends on it.
- Store hooks: `on_rebalance(assigned, revoked, newly_assigned)` runs from `TableManager.on_rebalance` before the recovery
  manager rebuilds its active/standby sets (faust/tables/manager.py:187-206, faust/tables/base.py:623-631).
  `on_recovery_completed(active_tps, standby_tps)` gets the per-table sets from recovery (faust/tables/recovery.py:624-637,
  faust/stores/base.py:80-84).
- The Kafka assignment, which is where `assigned` and `revoked` come from, holds actives plus standby changelog partitions
  (faust/assignor/client_assignment.py:108-117, faust/app/base.py:1870, faust/app/base.py:1896-1898).
- GlobalTable changelog partitions are all actives on every worker, and they are also standbys: all of them when
  `synchronize_all_active_partitions` or `use_partitioner` is set, otherwise the ones not already active
  (faust/assignor/partition_assignor.py:312-345).
- In-memory store today: it records a key's partition only on the changelog-apply path (faust/stores/memory.py:16, faust/stores/memory.py:54).
  It purges keys outside the active partitions once, at recovery completion (faust/stores/memory.py:57-70).
  Its `on_rebalance` is the base no-op (faust/stores/base.py:70-78).
- RocksDB store today: iteration and len go through `_dbs_for_actives`, which uses `app.assignor.assigned_actives()`
  plus an `is_global` bypass (faust/stores/rocksdb.py:679-694, faust/stores/rocksdb.py:725-735). Revoked dbs are popped at
  `on_rebalance` (faust/stores/rocksdb.py:547-589). Newly assigned non-standby dbs are opened at `on_rebalance`
  (faust/stores/rocksdb.py:591-608).

## Result: GREEN

Wrong-by-default decisions (kind, file:line, separating input):
- #2 K1, faust/stores/rocksdb.py:565 + faust/assignor/client_assignment.py:111-117: `assigned` includes standbys and `revoked` misses active→standby demotion. Input: P1 demoted to standby on the same worker, its keys still readable.
- #3 K5, faust/stores/memory.py:57-70 + faust/stores/rocksdb.py:680: the visible set changes at the wrong moment. Input: in-memory shows revoked P0 and half-recovered P2 during recovery. RocksDB shows a regained P2's stale on-disk keys before recovery is done.
- #4 K3, faust/stores/memory.py:54 (the only `_key_partition` write): locally written keys have no partition. Input: `table["a"]=1` on P1, P1 revoked → `"a" in table` stays True.
- #5 K3, faust/stores/memory.py:21-40 + faust/tables/recovery.py:850-892: standby replication after completion re-adds hidden keys. Input: standby P3 record "z" after completion → "z" visible.
- #7 K2, faust/stores/rocksdb.py:509 and faust/stores/rocksdb.py:661: no-event point reads search every open db. Input: timer `table.get("z")` for a standby-partition key returns a value.
- #8 K3, faust/stores/rocksdb.py:686 + faust/stores/memory.py:33: the crash also comes from RocksDB's live `_dbs` dict and from in-memory recovery inserts. Input: RocksDB `for k,v in table.items(): await sleep(0)` with a revoke mid-walk → RuntimeError.
- #9 K5 (lower confidence, `use_partitioner` only), faust/stores/rocksdb.py:475-477 vs faust/tables/table.py:86-88: event partition vs changelog partition. Input: key hashed to changelog P3 from source P0, P3 lost → key stays.

Rated none:
- #1 store-level placement: the RocksDB sibling decides it right.
- #6 GlobalTable exemption: `is_global` bypass and "in actives" are right. A standby-set rule is only a trap off the nearest path.
- #10 kept partitions: both stores keep them.
- #11 windowed key-index table: right through the shared sites, and inherits #4.
- #12 SetTable: would be K3, but not counted because scope is contested.
- #13 interrupted recovery: right as is. The stale-generation race is not a findable store decision.
- #14 restart / on-disk state: right as is.
